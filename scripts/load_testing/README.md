# Независимая система нагрузочного тестирования FastAPI (Lerne TMA)

Данный модуль предоставляет полностью изолированную, воспроизводимую систему нагрузочного тестирования для API-обработчиков FastAPI.
Система предназначена для измерения производительности (throughput, p50/p95/p99, стабильность соединений, ошибки) и сравнения метрик **до и после оптимизаций Codex** (например, пул соединений Peewee, worker threads, async I/O).

---

## 1. Сценарии нагрузки и профили

Система моделирует ключевые рабочие потоки пользователей:

1. **`study` (Учебный цикл: next + grade):**
   - `GET /api/decks/{deck_id}/next?review_context=scheduled` — выбор карточки по SRS алгоритму.
   - `POST /api/study/grade` — сохранение оценки (SRS интервал, repetitions, review history) с `return_next: true`.
2. **`read` (Чтение карточек):**
   - `GET /api/decks/{deck_id}/cards` — чтение списка всех карточек колоды.
   - `GET /api/study/card/{card_id}` — загрузка детального представления карточки для сессии.
3. **`sync` (Офлайн-синхронизация v2):**
   - `GET /api/sync/v2/pull` — чтение дельты изменений сервера.
   - `POST /api/sync/v2/push` — пакетная отправка прогресса изучения и событий оценок с уникальным `request_id`.
4. **`mixed` (Реалистичная смешанная нагрузка):**
   - 50% учебные действия (next + grade)
   - 35% чтение карточек
   - 15% офлайн-синхронизация

---

## 2. Поддерживаемые уровни параллелизма (Virtual Users)

Сценарии воспроизводятся на фиксированных ступенях параллелизма:
- **1 VU** — базовая одиночная нагрузка (эталон чистой латентности без конкуренции).
- **10 VU** — умеренная конкурентная нагрузка.
- **50 VU** — высокая конкурентная нагрузка (проверка насыщения пула Peewee).
- **100 VU** — стресс-тест под пиковой нагрузкой (проверка очередей соединений и тайм-аутов).

---

## 3. Измеряемые метрики

Для каждого сценария, каждого уровня VU и каждого отдельного эндпоинта вычисляются:
- **Throughput:** запросов в секунду (RPS / req/s).
- **Латентность (мс):**
  - `p50` (медиана)
  - `p90`
  - `p95` (критическая латентность для 95% пользователей)
  - `p99` (хвостовая задержка / tail latency)
  - `min`, `max`, `mean`
- **Ошибки и надёжность:**
  - Процент ошибок (`error_rate_pct`).
  - Распределение HTTP-статусов (200, 4xx, 5xx).
  - Классификация сетевых ошибок (`ConnectTimeout`, `ReadTimeout`, `PoolTimeout`, `ConnectionReset`).
- **Метрики соединений:**
  - Пиковое число активных одновременных HTTP-соединений.
  - Соединения с базой данных (при тестировании с локальным PostgreSQL):
    - `peak_active_db_connections` — активные запросы в PostgreSQL (`pg_stat_activity`).
    - `peak_total_db_connections` — общее число соединений бэкенда к БД.
    - `peak_waiting_queries` — запросы, заблокированные в ожидании блокировок/пула.

## 4. Безопасность и синтетические данные

- **Только локальное тестовое окружение:** скрипты защищены проверкой `_assert_environment_safety()` и категорически блокируют запуск, если обнаружено окружение `ENVIRONMENT=production` или `VERCEL`.
- **Изолированный пул пользователей:** виртуальные пользователи создаются в выделенном синтетическом диапазоне ID `980000001` .. `980000120`. Они не пересекаются с реальными пользователями или локальным пользователем разработки (`900000001`).
- **Авторизация:** каждому виртуальному пользователю генерируется персональный токен сессии (`TMAAuthToken`), действующий для авторизации через заголовок `Authorization: Bearer la_...`.
- **Полная очистка:** команда `--cleanup` полностью удаляет все синтетические токены, сессии, колоды, карточки, прогресс и пользователей.

## 5. Быстрый старт и пошаговая инструкция запуска

### Шаг 1. Подготовка синтетических данных

В терминале PowerShell установите режим `LOCAL` и сгенерируйте данные для 100 виртуальных пользователей:

```powershell
$env:LERNE_MODE="LOCAL"
python -m scripts.load_testing.seeder --seed --users 100
```

Проверить статус генерации:
```powershell
python -m scripts.load_testing.seeder --status
```

### Шаг 2. Запуск тестового сервера FastAPI

В отдельном окне терминала запустите сервер приложения:

```powershell
$env:LERNE_MODE="LOCAL"
uvicorn api.main:app --host 127.0.0.1 --port 8000
```

*(Если вы хотите запустить тест без запуска внешнего HTTP-сервера, например в CI или без сетевых портов, используйте флаг `--in-process`, см. ниже).*

### Шаг 3. Запуск нагрузочного тестирования (Baseline)

Запуск полного набора сценариев для 1, 10, 50 и 100 пользователей по 15 секунд на ступень:

```powershell
$env:LERNE_MODE="LOCAL"
python -m scripts.load_testing.runner --target-url http://127.0.0.1:8000 --users 1,10,50,100 --duration 15 --output local/test-data/load_test_results/baseline.json
```

Параметры запуска:
- `--target-url`: URL сервера FastAPI (по умолчанию `http://127.0.0.1:8000`).
- `--in-process`: запуск внутри процесса через `httpx.ASGITransport` (без запуска Uvicorn).
- `--users`: список ступеней нагрузки (например, `1,10,50,100`).
- `--duration`: длительность каждой ступени в секундах (по умолчанию 15).
- `--scenarios`: сценарии через запятую (`study,read,sync,mixed`).
- `--output`: путь для сохранения результатов в формате JSON.
- `--think-time`: пауза между запросами пользователя в секундах (по умолчанию `0.0` для стресс-теста максимального RPS).

### Шаг 4. Запуск тестирования на ветке с оптимизациями (Codex)

После применения изменений Codex (например, ветка `codex/c1-fastapi-db-workers`), повторите запуск:

```powershell
python -m scripts.load_testing.runner --target-url http://127.0.0.1:8000 --users 1,10,50,100 --duration 15 --output local/test-data/load_test_results/codex.json
```

### Шаг 5. Сравнение результатов (Baseline vs Codex)

Запустите инструмент сравнения:

```powershell
python -m scripts.load_testing.compare local/test-data/load_test_results/baseline.json local/test-data/load_test_results/codex.json --output comparison.md
```

Скрипт выведет форматированную Markdown-таблицу со всеми дельтами (RPS, p50, p95, p99, ошибки) и итоговым вердиктом (`[IMPROVED]`, `[DEGRADED]`, `[SIMILAR]`).

### Шаг 6. Очистка тестовых данных

После завершения тестирования удалите все синтетические данные:

```powershell
python -m scripts.load_testing.seeder --cleanup
```

## 6. Что делать, если тестовая среда недоступна

Если локальный сервер PostgreSQL или Uvicorn недоступен:
1. **Проверка доступности локального PostgreSQL:**
   - Порт по умолчанию: `127.0.0.1:55432`.
   - Проверка: `python -c "import socket; s = socket.socket(); print('DB Port Ready:' if s.connect_ex(('127.0.0.1', 55432)) == 0 else 'DB Port Unavailable')"`
   - Запуск нативной службы PostgreSQL (если установлена в проекте): `C:\121\Lerne_projekt\tools\pgsql\bin\pg_ctl.exe -D C:\121\Lerne_projekt\data\postgres start`.
2. **Запуск в режиме in-process (ASGITransport):**
   - Если Uvicorn не запущен на порту 8000, добавьте флаг `--in-process`. Тестовый раннер напрямую нагружает FastAPI middleware, роутеры, зависимости, сервисы и БД.
3. **Честная фиксация ограничений:**
   - Если сервер БД недоступен, скрипты раннера выдадут чёткое сообщение с описанием проблемы. Зафиксируйте в отчёте: «БД PostgreSQL была недоступна на порту 55432, тест проводился в изолированном mock/in-process окружении».
