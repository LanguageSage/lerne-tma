# Локальная админка: снижение Egress и безопасные скрипты

Проверено 20 октября 2026 на изолированных данных в памяти. Production Supabase не опрашивался, миграции данных не запускались, деплой не выполнялся. Фактический тарифицируемый Egress до/после не измерен. Ниже — локально измеренные SQL-вызовы и размеры полезных данных, а не оценка счёта Supabase.

## Измерение до/после

Базовый код: commit `0ffd2b37318ce741d2706385fd1a3823ce39b7f4`. Тест исполняет старые функции и новые на одной фикстуре. Размер SQL-данных — сумма UTF-8/бинарных значений извлечённых строк, без протокольного overhead, TLS, служебных запросов драйвера и биллинговых правил. JSON измерен сериализацией ответа. Runtime-диагностика отдельно считает фактические байты ASGI response body.

Превью: 120 карточек с контекстами примерно 16 КБ и `image_data` 32 КБ; новая страница — 50 карточек. Тексты искусственные.

| Операция | SQL до | SQL после | Прочитано до, байт | После, байт | JSON до, байт | После, байт |
|---|---:|---:|---:|---:|---:|---:|
| Превью, холодный запрос | 242 | 3 | 5 866 518 | 33 415 | 1 944 081 | 22 083 |
| Превью, следующая страница из кэша | — | 0 | — | 0 | — | 22 113 |
| Пользователи, 61 запись → страница 50 | 2 | 3 | 2 912 | 2 646 | 15 598 | 12 877 |
| Колоды, 61 запись → страница 50 | 4 | 4 | 6 486 | 4 164 | 23 883 | 19 666 |
| Папки, 61 запись → страница 50 | 4 | 4 | 9 505 | 3 462 | 20 449 | 16 873 |

Для второй страницы пользователей, колод и папок: 0 SQL и 0 прочитанных байтов; JSON соответственно 2 904 / 4 339 / 3 830 байт. Число запросов пользователей на холодном кэше выросло на один: отдельная проверка реального отсутствия аккаунтов устраняет ошибочную выдачу существующих пользователей как гостей после поиска.

Причины перерасхода:

- `get_deck_and_cards()` загружал все поля и бинарные изображения даже для превью и операций, которым нужен только ID колоды.
- Проверка аудио выполнялась дважды на карточку: 240 отдельных SQL-вызовов для 120 карточек. Теперь имена аудио проверяются одним запросом.
- Полные контексты/история/metadata передавались для списка; превью теперь содержит фрагменты по 240 символов, редактор запрашивает полный текст отдельно. Поиск проверяет полный текст в БД.
- Списки пользователей и папок выбирали все поля пользователей; папки считали карточки по всей БД даже при фильтре владельца. Проекции и агрегаты сужены.
- Миграции изображений и аудио заново выбирали одни и те же ошибочные строки без курсора; HTTP 400 мог приводить к бесконечной передаче данных.
- Backup Storage не имел HTTP-таймаутов; bucket-copy не ограничивал полный проход/объём копируемых объектов.

## Пагинация и кэш

Четыре list API возвращают `page`, `limit` (1–200), `total`, `has_more`. Поиск и фильтры применяются перед страницей, общие показатели колоды/папок сохраняются. Существующая пагинация галереи не изменена.

Пагинация выполняется сервером по компактным RAM-снимкам. На холодном кэше читаются все компактные строки соответствующей выборки: это **не SQL LIMIT/OFFSET для каждого списка**. Такой вариант сохраняет глобальную статистику и совместное применение фильтров без чтения больших полей. Кэш ограничен 32 ключами и TTL 60 секунд; записи/commit/rollback из этого процесса его сбрасывают. Изменения через другой процесс могут оставаться невидимыми до TTL. Для существенно больших каталогов следующий шаг — перенос фильтров агрегированной статистики в SQL и пагинация самих компактных строк.

Автор, импорт, назначение и выбор отдельных карточек для генерации получают полный компактный каталог только при открытии соответствующего действия. Загрузка идёт конечными страницами, максимум 20 000 записей; при превышении возвращается явная ошибка. Обычные экраны используют одну страницу. Автообновление колод не выполняется в скрытой вкладке.

Диагностика: `GET /api/admin/diagnostics` с обычным локальным Origin. Последние 100 запросов; числа запросов/строк, приблизительные SQL-байты, точные байты HTTP-body, время и 10 самых тяжёлых операций. Нет SQL-текста, параметров, payload карточек, токенов, имён файлов или PII. Состояние хранится в RAM. Libpq-подключения локального процесса имеют defaults `PGCONNECT_TIMEOUT=10`, `statement_timeout=30000`, `lock_timeout=5000`; явно заданные настройки окружения сохраняются. Эти libpq defaults не гарантируют таймаут для альтернативного pg8000-драйвера.

## Миграции медиа

Безопасный пример запуска (сохранение исходного content):

```powershell
venv/Scripts/python.exe scripts/migrate_images_to_storage.py --max-records 100 --max-bytes 67108864 --attempts 3 --max-seconds 300 --report images-migration-report.json
```

По умолчанию: 100 записей, 64 МиБ бюджета payload, 3 попытки на запись, 300 секунд HTTP-прохода. Допустимо максимум 10 000 записей и 5 попыток; все значения проверяются до доступа к БД. Бюджет резервирует чтение бинарника, каждую попытку upload, проверочный download и передачу исходного бинарника для compare-and-clear. Он консервативен и не включает SQL/HTTP/TLS overhead; контроль размера перед чтением не является гарантией против конкурентного увеличения blob другим процессом. У сетевых запросов собственные конечные connect/read/total timeout.

Проход идёт по возрастанию ID. Неудачная строка повторно не выбирается в том же запуске. JSON-отчёт содержит ID, безопасную причину, stop reason, last_id и счётчики. `--after-id` позволяет продолжить проход; для повторной обработки ошибок можно запустить с начала — обнулённые строки уже не выбираются. Существующий объект не перезаписывается; после успешной загрузки либо конфликта проверяются публичная доступность, размер и SHA-256. Пустой, недоступный, отличающийся или конкурентно заменённый blob не очищается.

**Очистка БД только с `--clear-db-content`.** До использования этого флага серверы, обслуживающие TMA и админку, должны иметь новый Storage-key reader. По умолчанию успешная проверка оставляет исходный бинарник. Это позволяет подготовить перенос без немедленного деплоя и без повреждения ссылок на старом сервере. В этой задаче флаг против Production не выполнялся.

Кириллические имена получают ASCII-ключ `legacy-<sha256(filename)>.ext`; `TMAMedia.filename`, image_path, inline-ссылки и JSON V2 не переписываются. `/api/media/images/...` разрешает этот ключ после очистки; ASCII-имена и старые пути сохраняются. Admin download/ZIP умеют читать мигрированные изображения из Storage с лимитом размера. ZIP ограничен 64 МиБ, отдельный файл — 25 МиБ. Legacy zstd распаковывается с лимитом перед переносом.

`migrate_cyrillic_images.py` теперь вызывает безопасную миграцию и не делает частичных SQL replace в front_text. `migrate_audio_to_storage.py` использует тот же механизм и действующий бакет `audio`; неподдерживаемые не-ASCII имена аудио сохраняются в БД и попадают в отчёт. `migrate_audio_bucket.py` копирует максимум 100 объектов/64 МиБ по metadata.size, ограничивает list 1000 объектами и общий run 300 секундами; оригиналы не удаляет. `backup_cloud_storage.py` имеет лимиты, таймауты, безопасные пути и не перезаписывает существующие файлы. Исторические скрипты в `scripts/archive/` не запускались и не объявляются безопасными.
