# Задача 2.2: надёжность серверных операций

## Проверенный риск

Аудит от 22.10.2026, исходный `main`: `b01e84c`. Проверены последние коммиты
и вызовы `create_task`, `ensure_future`, `BackgroundTasks`, `add_task`,
`Thread` и `submit` в `api/**/*.py`. Найдены два запуска работы после ответа:
переклассификация CEFR и автоматическое аудио при `/cards/save`.
Awaited batch generation, evaluation и непосредственные media endpoints
не являются fire-and-forget и по этой причине не переделывались.

`asyncio.create_task` не связывает окончание работы с ответом HTTP.
FastAPI/Starlette `BackgroundTasks`, напротив, прикреплены к ASGI response:
неверно утверждать, что Python обязательно останавливается сразу после отправки
ответа. Но это внутрипроцессное выполнение без долговечной очереди, а ошибка
после отправки ответа уже не может превратить его в отказ.
Остановка экземпляра, общий дедлайн функции и сбой процесса остаются рисками.

Источники: [Starlette Background](https://starlette.dev/background/),
[ошибки после ответа](https://starlette.dev/exceptions/),
[Python runtime Vercel](https://vercel.com/docs/functions/runtimes/python),
[ограничения Vercel Functions](https://vercel.com/docs/functions/limitations).
`waitUntil` продлевает выполнение в пределах жизненного цикла функции,
но сам по себе не даёт восстановления после падения. Новые сервисы не подключены.

## Реализованная переклассификация

- `POST /cards/classify-batch` сохраняет `deck_id` / `card_ids` и
  `target_language`. Добавлены `operation_id` (UUID) и `batch_index` (с нуля).
  Старый вызов без UUID допустим, сервер возвращает созданный UUID; для безопасного
  повтора клиент должен передать его обратно. Колода имеет прежний приоритет
  над `card_ids`. Аутентификация и collaborative permissions сохранены.
- За запрос обрабатывается максимум 10 карточек. Локальный порог `.80` и CEFR
  metadata сохранены. Неуверенные карточки отправляются одним awaited AI-вызовом.
  Его дедлайн — 20 секунд, transport — 18 секунд, один ключ, одна попытка.
  Только переклассификация включает `strict=True`: ошибка, отсутствующая модель,
  невалидный или неполный JSON не превращаются в фиктивный `A1`. Legacy callers
  классификатора сохраняют прежнее поведение.
- Снимок ID, оставшиеся ID, попытки, lease и последний ответ сохраняются в
  **существующей** `TMAOfflineBatch` под ключом `classify:{user_id}:{operation_id}`.
  Это новое назначение существующей квитанции, без новых таблиц или миграций.
  Отпечаток scope исключает повтор UUID с другой выборкой или языком.
- Compare-and-swap квитанции даёт единственного исполнителя одного пакета.
  Транзакции короткие, в одном потоке/connection; во время AI транзакция не открыта.
  Запись карточек и нового прогресса атомарна. Потерянный ответ воспроизводится
  без повторного AI и без повторной записи. Старый исполнитель после нового claim
  не может закоммитить устаревший результат.
- После отмены/падения lease освобождается по времени через 60 секунд. Максимум
  три исполнения незавершённой карточки за серию; после лимита можно продолжить
  спустя 5 минут. Ошибки не вызывают автоматический цикл повторов.
- До записи повторно проверяются права, удаление, колода, FRONT, tags, metadata
  и `updated_at`. Изменяются только CEFR tags/metadata и timestamp. Параллельная
  правка карточки не перезаписывается; изменённая карточка остаётся незавершённой.
- Ответ содержит `status=more|partial|busy|ok`, `complete`, `completed_count`,
  `total_count`, `remaining_count`, `next_batch`, `error_code`, `cards` и
  `updated_count` текущего пакета. `pending_background_count` оставлен для
  совместимости и всегда равен нулю. Только `ok` + `complete=true` означает конец
  всей операции; HTTP 200 с `partial` не означает успех.
- Оба меню используют `reclassificationService.js` через авторизованный
  `networkApi`. UUID/номер пакета записываются в localStorage **до** первого
  запроса, отдельно для аккаунта/колоды/языка. Успешные пакеты идут последовательно;
  ошибки останавливают цикл. Повтор «Обновить CEFR-уровни», в том числе после
  перезагрузки страницы, продолжает прежний UUID. Повторные клики в одном клиенте
  разделяют текущую операцию. Смена аккаунта прекращает цикл.

Пример: после 5 подтверждённых пакетов из 100 карточек прогресс равен 50/100.
При обрыве шестого запроса нет уведомления о завершении. Повтор либо воспроизводит
закоммиченный шестой ответ, либо ждёт истечения lease и обрабатывает тот же пакет.
Предыдущие 50 карточек больше не посылаются AI.

## Ограничения

Это возобновление по действию пользователя, не автономная очередь. Закрытие
страницы останавливает отправку следующих пакетов. Очистка localStorage теряет
клиентский указатель на UUID, хотя квитанция остаётся на сервере. Новые карточки,
добавленные после старта, не входят в снимок. Удаление/перемещение или утрата прав
на незавершённые карточки требует разрешить конфликт либо начать новый UUID
через API; интерфейс автоматического сброса таких операций здесь не добавлен.

База гарантирует отсутствие повторной записи результата в пределах UUID.
Она **не может гарантировать exactly-once оплату у AI-провайдера**: если провайдер
принял запрос, а процесс упал до коммита, после lease возможен ещё один вызов.
Количество ограничено дедлайнами, размером пакета и лимитом попыток. Новая явная
операция с другим UUID может повторно классифицировать ту же карточку.

## Аудио: необходимая отдельная доработка

Автоматическое аудио в `api/routers/cards.py` **не исправлено этим изменением**;
`BackgroundTasks` и соответствующий риск остаются. Это допустимое в задаче
выделение отдельной доработки, а не утверждение о надёжной очереди.

Причины, по которым простая замена на `await ensure_card_audio(...)` недостаточна:

1. `api/services/media.py::ensure_card_audio` подавляет ошибки и может записать
   только filename файла из `/tmp/pending_audio`, без долговечного media record.
   Ожидание такого результата не доказывает готовность аудио после холодного старта.
2. Сервис сохраняет полученный до ожидания объект карточки целиком. Необходимо
   заново проверить доступ, актуальность FRONT и записывать только audio-поле.
3. Карточка к этому моменту уже сохранена. Возвращать обычную ошибку всего save
   опасно: повтор создания без ID способен создать другую карточку. Нужен отдельный
   результат `card_saved` / `audio_status` и понятное предупреждение в потребителях
   save, с повтором аудио по **существующему** card_id.

Конкретный следующий объём: awaited TTS с дедлайном; долговечное сохранение
в существующий Storage/TMAMedia; повторная проверка прав/FRONT; update только audio;
раздельный результат сохранения карточки/аудио и сообщение в UI; повтор аудио по
card_id с использованием существующего кеша, без повторного создания карточки.
Проверки: сбой TTS, сбой хранения, обрыв после сохранения карточки, смена текста/
прав, повтор и доступность файла после холодного старта.
Для этого не требуется новая таблица/очередь, если допустимо дождаться TTS в HTTP.
Автономное восстановление без участия клиента потребует отдельно согласованной
долговечной очереди. В этой задаче редактор и параллельные изменения локальной
БД/медиа не затрагиваются.
