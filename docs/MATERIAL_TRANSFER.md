# Управляемый перенос и публикация материалов

## Назначение и состояние

Раздел **«Перенос и публикация»** в локальной административной консоли переносит
папки, колоды и выбранные карточки между LOCAL и явно настроенным проектом
Supabase. Экспорт файлов и манифесты не нужны. Это обслуживание учебного контента,
а не двусторонняя синхронизация пользователей.

По умолчанию подключения нет и облачная запись отключена. В рамках разработки
рабочий Supabase не подключался, не изменялся и не развёртывался.

## Однократная настройка оператора

1. Используйте существующий LOCAL и его обычную команду admin:
   `venv/Scripts/python.exe scripts/local_dev.py admin`.
2. Рядом с внешним `config/local.json` создайте `config/transfer.json`.
   Этот файл находится **вне Git**, не в `local/` репозитория. Для стандартного
   размещения: `C:\121\Lerne_projekt\data\config\transfer.json`.
3. Пример с вымышленными значениями, первоначально для изолированного staging:

```json
{
  "enabled": true,
  "environment": "staging",
  "project_ref": "abcdefghijklmnopqrst",
  "database_url": "postgresql://postgres:REPLACE@db.abcdefghijklmnopqrst.supabase.co:5432/postgres?sslmode=require",
  "storage_url": "https://abcdefghijklmnopqrst.supabase.co",
  "storage_key": "REPLACE_SERVER_SIDE_ONLY",
  "cloud_user_id": 123456789,
  "allow_cloud_write": false
}
```

`cloud_user_id` — существующий подтверждённый аккаунт **Lerne**, от имени которого
оператор обслуживает материалы. Он задаётся на доверенной машине, браузер его
не присылает. Перенос проверяет обычные owner/editor/global_readonly permissions.
`storage_key` предназначен только для серверной загрузки в существующие buckets
`images` и `audio`. Ограничьте доступ к конфигурации средствами ОС. База и Storage
должны принадлежать одному `project_ref`; PostgreSQL использует TLS. Допускается
также Supabase pooler с username `postgres.<project_ref>`.

Схема должна уже содержать обычные таблицы Lerne, включая `TMAOfflineBatch`.
Перенос **не запускает миграции**, не создаёт таблицы или buckets и не читает
репозиторный `.env`. LOCAL должен иметь прежний `LOCAL_DATABASE_MARKER`.
Нестандартный platform-admin ID из облачного deployment автоматически не
импортируется: worker использует существующую политику `api.permissions` с её
штатным ID. Такой deployment требует отдельной проверки политики до включения.

## Как пользоваться

1. Откройте `http://127.0.0.1:8050` → **«Перенос и публикация»**.
2. Выберите направление и вид материалов. Нажмите **«Показать материалы»**;
   поиск, страницы по 50 строк и флажки позволяют выбрать нужный пакет.
   При необходимости выберите целевую папку по имени. Она служит родителем
   переносимого дерева; существующие сопоставления имеют приоритет.
   Списки кешируются сервером на 5 минут (включая страницы/поиск и целевые папки).
   Возврат на вкладку сохраняет список и выбор. Повторные одновременные запросы
   используют один результат; ошибка подключения имеет паузу 10 секунд.
   Настройка проекта меняет ключ кеша, успешный перенос очищает списки.
3. Выберите обновление контента и медиа: только недостающие, недостающие и
   изменённые либо принудительная замена выбранных. При совпадении можно
   пропустить, заменить или добавить карточку как новую независимую копию.
4. Нажмите **«1. Проверить перед копированием»**. Проверка выполняется в фоне:
   браузер показывает время ожидания, опрашивая только локальное состояние.
   Одинаковый предпросмотр переиспользуется до 5 минут; одновременные проверки
   не запускаются. Ошибки показываются над списком с прокруткой к сообщению.
   Пакет больше 200 папок, 1000 колод или 2000 карточек нужно разделить:
   выбрать вложенную папку или несколько колод. Размер проверяется до чтения
   содержимого карточек и подготовки медиа.
   Раскройте строки: отображаются
   исходный/целевой ID, действие, поля «было/станет», структура и медиа.
   Подготовка медиа может сохранить проверенные файлы в LOCAL-кэш;
   облачная запись и привязки карточек в этот момент не выполняются.
5. Если целевая версия была изменена отдельно, замена требует явного разрешения
   конфликтов и нового предпросмотра. Проверяйте также soft-delete и перемещения.
6. Итог проверки, подтверждение и кнопка **«2. Начать копирование в LOCAL»**
   (либо «Начать публикацию в Supabase») находятся перед подробным списком.
   Для применения введите точную показанную цель, например
   `Supabase:abcdefghijklmnopqrst`, и включите флажок подтверждения.
   Запись в облако дополнительно требует серверного `allow_cloud_write: true`.
7. Наблюдайте прогресс и итог. После сбоя откройте **ту же сохранённую операцию**
   и повторите подтверждение. Устаревший предпросмотр нужно пересоздать.

В локальном редакторе и при изучении доступна кнопка **«Опубликовать в Supabase»**.
Редактор сначала сохраняет правку, затем существующая Dexie-синхронизация доводит
её до LOCAL PostgreSQL. Открывается административная консоль с выбранной одной
карточкой; запись всё равно требует предпросмотра и подтверждения. Для нового
отрицательного offline ID сначала требуется обычное сохранение/синхронизация.

## Авторские оригиналы и личные копии

Существующая модель прав сохранена: `global_readonly` позволяет всем читать и
изучать оригинал; менять его может владелец опубликованного корня или штатный
platform admin. Для частных материалов действуют owner/editor и наследование
collaborator. Авторство само по себе не даёт права редактирования.

Публикация новой общедоступной папки — отдельный флажок, доступный только
администратору. Без него новые папки частные. Обычное копирование в библиотеку
по существующим share/copy API создаёт независимую редактируемую копию;
перенос не обновляет такие пользовательские копии. Co-op остаётся в облаке.

На новой целевой записи владелец — явно настроенный аккаунт назначения.
Автор из пары LOCAL↔cloud переводится в соответствующий аккаунт; неизвестный
автор получает `metadata.author_origin` с исходной базой и ID вместо приписывания
ему чужого числового ID. При обновлении существующий creator сохраняется.
Пользователи, collaborators и grants между базами не копируются.

## Целостность и восстановление

- Переносятся только поля содержимого из `FIELDS` в `material_transfer.py`.
  `TMAProgress`, review history, knowledge attempts/mastery, оценки, flags,
  bookmarks, auth sessions, настройки пользователей и секреты не экспортируются.
  Подозрительные ключи состояния/секретов в metadata блокируют перенос.
- ID разных баз никогда не сопоставляются по числу, названию или тексту.
  LOCAL `TMAOfflineBatch` хранит namespace пары баз/аккаунтов, соответствия ID,
  контрольные суммы контента, родителей и версию соответствия. Не удаляйте
  transfer receipts при обслуживании обычной offline-очереди.
- `updated_at` и полный снимок участвуют в проверке свежести. SHA-256 содержимого
  исключает лишние UPDATE при изменении лишь технического timestamp. Исходные
  данные и permissions проверяются повторно; целевые строки проверяются под
  PostgreSQL row locks в той же транзакции, что записывает контент и receipt.
  Изменение цели во время передачи медиа отменяет запись контента.
  Время карточек/родителей берётся из целевой БД, чтобы часовой пояс оператора
  не создавал будущие или запаздывающие sync timestamps в другой базе.
- Структура, порядок, паспорт и metadata колод сохраняются. Одиночная карточка
  использует существующие папки/колоду как зависимости и не перезаписывает
  их паспорт. Ранее сопоставленные дети, перемещённые за пределы выбранной
  папки/колоды, включаются в предпросмотр вместе с новым путём.
- Удаление переносится только как существующий soft-delete tombstone. Отсутствие
  строки или потерянный mapped ID не означает разрешения удалить/создать её
  заново: операция блокируется. Физических удалений нет, циклы папок запрещены.
- Cloud content + receipt коммитятся атомарно. Если процесс оборвался до
  сохранения LOCAL-сопоставления, повтор читает облачный receipt и восстанавливает
  соответствие без новых карточек. До разрешения прерванной записи новый preview
  блокируется. PostgreSQL advisory lock ограничивает перенос одним worker.
- `Добавить как новую` сохраняет соответствие оригинала, а повтор **того же**
  подтверждения не создаёт ещё одну копию. Новый подтверждённый preview с этим
  действием означает новое намеренное копирование.
- LOCAL API и admin сохраняют сетевой запрет. Только отдельный короткоживущий
  worker получает внешнюю конфигурацию. Прокси Peewee переключаются исключительно
  в этом процессе, отдельно от HTTP-потоков. Админка сохраняет loopback/Host/
  Origin guard; ключи и DB URL не попадают в браузер или сообщения ошибок.

## Медиа и ограничения пакета

Переиспользуются `prepare_media` / `store_media` folder importer, LOCAL media root
и `TMAMedia`. Медиа получают неизменяемые `import_<sha256>.<ext>` имена. Изображения
проверяются/оптимизируются существующим WebP-конвейером, аудио проверяется по
сигнатуре. Поддерживаются пути `/api/media`, обычные legacy filenames и публичные
URL настроенного Supabase Storage; переносятся также ссылки в контексте и
`metadata.resources`. Старые embedded `image_data` преобразуются в медиафайл.

Storage HEAD/ETag и SHA-256 определяют версии. Для PostgreSQL blob checksum
вычисляется на сервере без повторного чтения бинарника клиентом. Проверенные
исходные версии и подготовленные файлы кешируются в LOCAL. Неизменённый файл
не скачивается и не загружается повторно; отсутствующий объект с оставшимся
каталогом ремонтируется. Замена создаёт новый immutable key и новую привязку,
не перезаписывая файл других карточек. Это относится и к force: одинаковые байты
переиспользуются. Автоматических повторов HTTP нет; ошибки требуют явного retry.

Один пакет: до 200 папок, 1000 колод, 2000 карточек, 500 медиа, 20 МБ на исходный
файл и 100 МБ подготовленных медиа. Предпросмотр действует один час. Списки
не содержат blobs, полных карточек или секретов.

Ограничения: видео, private/signed Storage URLs, внешние media-хосты и вложенные
объектные пути Storage пока отклоняются. Legacy library `Deck`/`Card` не являются
целью переноса — поддерживается авторский `TMA_*` контент. Импорт ранее вручную
созданной дублирующей LOCAL-колоды не угадывает её соответствие облачной:
начните с загрузки исходной облачной колоды. После отказа между загрузкой media
и content commit могут остаться безопасные неподключённые immutable assets;
ими управляет существующий media manager. Атомарной транзакции сразу между
двумя PostgreSQL и Storage нет; восстановление обеспечивает receipt.

## Проверки и включение Production

Изолированные suites запускаются через существующий безопасный harness без
редактирования пользовательских изменений в `scripts/test_backend.py`:

```powershell
venv/Scripts/python.exe -c "from scripts.test_backend import isolated_suite; raise SystemExit(isolated_suite('scripts/tests/test_material_transfer.py'))"
venv/Scripts/python.exe -c "from scripts.test_backend import isolated_suite; raise SystemExit(isolated_suite('scripts/tests/test_material_transfer_boundary.py'))"
venv/Scripts/python.exe scripts/tests/run_material_transfer_postgres.py --bin-dir C:/121/Lerne_projekt/tools/pgsql/bin
npx --no-install playwright test --config scripts/tests/browser/admin-transfer.config.cjs
npx --no-install playwright test --config scripts/tests/browser/local-publish.config.cjs
```

PostgreSQL runner создаёт **новый** временный кластер со случайным loopback-портом
и синтетическими БД, затем останавливает и удаляет только его. Браузерный стенд
на 8061 использует две SQLite-базы и подменённый bridge, без внешних запросов.

Проверяются оба направления и три уровня выбора, независимость ID, неизменённый
повтор, skip/replace/copy, конфликты и свежесть, перемещения/порядок/tombstones,
паспорт, SRS, медиа/дедупликация, rollback, потеря ответа и permissions. HTTP-suite
проверяет Origin, конфигурацию/неразглашение ключей, запрет клиентского actor ID
и локальное действие карточки. Browser-suite — 320/375/430/768/1440 px,
выбор, diff, подтверждение точной цели, ошибку/retry и вход с одной карточкой.
Отдельный React fixture на 5183 без Vite HMR проверяет порядок save → sync → admin
preview и скрытие действия для viewer; auth/API/sync подменены. Работающий
пользовательский LOCAL на 5173 не останавливается. Проверка пакетного чтения
подтверждает постоянное число запросов снимка при увеличении числа карточек;
повтор неизменённого материала не выполняет UPDATE карточек или SRS.

Результат проверки 22.10.2026:

| Проверка | Результат |
| --- | --- |
| Transfer: две SQLite-базы | 20/20 |
| Те же сценарии: новый PostgreSQL 17.11 cluster | 20/20 |
| HTTP/configuration/permission boundaries | 5/5 |
| Admin browser и React control/header fixture | 6 + 1, PASS |
| Существующие material permissions / folder importer / LOCAL / admin security | 31 + 23 + 19 + 10, PASS |
| Targeted ESLint, Python compilation, Vite build, diff check | PASS |

Для существующего folder-import suite изолированный harness сохранял блокировку
сети/нативного PostgreSQL, но очищал свой `VERCEL=1` перед выполнением тестов:
два LOCAL-кейса намеренно запрещают сочетание LOCAL+VERCEL. У остальных suites
не было такой адаптации. Сборка сообщает warnings о размере чанков и смешанных
static/dynamic imports. Полный набор старых live maintenance scripts не запускался.
Реальная Supabase/Storage и production credentials в проверках не использовались.

Перед разрешённым включением рабочей Supabase: проверить схему, аккаунт,
актуальную platform-admin policy и Storage на отдельном staging-проекте с
ограниченными серверными credentials; проверить backup/restore LOCAL и облака;
проверить реальный bridge/TLS и Storage egress/permissions. Эти внешние проверки
и интерактивный редактор LOCAL с настоящей auth/Dexie-сессией не заменяются
моками. После отдельного разрешения указать точный Production project_ref,
`environment: production` и включить `allow_cloud_write`. Подтверждение конкретных
изменений в админке остаётся обязательным. Деплой или merge для этого не нужен.
