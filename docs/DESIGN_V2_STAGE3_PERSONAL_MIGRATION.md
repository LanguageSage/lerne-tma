## Границы

Продолжение 2C в `main`. В начале работы 2C находился в рабочем дереве;
во время выполнения он появился в `HEAD` как `2b29195`. Этот этап не выполняет
commit/push/deploy и не меняет учебный контент, SRS, микрофон или схему Dexie.
Реальные пользовательские БД и browser storage не открывались для миграции.

Миграция реализуется при запуске обновлённого клиента, отдельно для каждого
аккаунта. Это подготовленный и проверяемый механизм, а не утверждение о переносе
данных всех существующих пользователей. Старые хранилища пока сохраняются.

У настроек дизайна не было отдельной Dexie-таблицы или очереди entity sync:
они доставлялись через `/user/settings`. Этап сохраняет этот отдельный поток,
сохраняет V2 локально перед отправкой и использует `networkApi` для подтверждения
доставки даже при включённом `offline_mode`. Синтетический offline `/init`
не считается серверным подтверждением настроек.

`backCardFontWeight`, `backCardFontStyle`, `backCardTextShadow` также учитываются,
если они присутствуют внутри переданного legacy-пресета. Они не добавлены
как новые настройки V1. Числовые строки размеров приводятся к числам.

Неизвестные и повреждённые значения не угадываются: runtime нормализуется
существующей V2-схемой, исходные данные остаются в backup. Deprecated V2
`exercises.bodyText` / `paletteMode` сохраняются; этот этап не удаляет их и
не меняет установленное в 2C использование явных V2-ролей/состояний.

Новая роль `front.matchRightText` необходима: V1 позволял разное оформление
левой и правой колонок, а V2 до этого этапа использовал `front.mainText` для обеих.
В старых опубликованных V2 JSON overrides пусты, поэтому их поведение сохраняется.
Контролы правой колонки размещены в существующей секции Match; сброс возвращает
наследование. Роль относится к `front`, поэтому переносится существующим
применением секций preset без изменения global/семантических состояний exercises.

## Приоритет оформления

Код до миграции задавал приоритет:

1. Включённый локальный admin draft.
2. Опубликованный V2.
3. Личное оформление, если опубликованного V2 нет.

Он сохранён в `resolveActiveDesign()` и `useSettingsStore.activeDesignConfig`.
Этот же config используется StudyCard, Speech, ExerciseRenderer, TrainerView,
CardForm, CardContentEditor, CardList и корневыми CSS-токенами.
Preview с явным config по-прежнему использует свой scoped draft.

Пустой `front.card.background` / `back.card.background` у публикации или draft
намеренно наследует соответствующий **личный V2 background**. Нормализация не
заменяет его defaults. Публикация с явно заданным фоном имеет приоритет.
Продуктового изменения приоритета или нового переключателя не добавлено.

При первом серверном чтении существующие серверные личные настройки имеют
приоритет над V1 этого браузера, как до миграции. Локальные и серверные источники
сохраняются отдельно. Изменения V2, сделанные offline, сохраняются для доставки.

## Запись, повтор и подтверждение

### Браузер

- `lerne:design-v1-source` хранит исходные строки V1 и владельца первого
  переноса. У старых ключей не было метаданных аккаунта: их исторического
  владельца невозможно доказать. После первого переноса они не копируются
  в следующий аккаунт; серверные настройки аккаунта остаются авторитетными.
- `lerne:personal-design:v2:<id>` содержит документ `{schemaVersion: 2,
  revision, config, preset}`, исходные snapshots, `pending`, `serverSeen`
  и базовый документ для слияния изменений.
- Backup и первоначальный V2 сохраняются одной записью localStorage;
  запись проверяется обратным чтением. При quota/повреждённом JSON миграция
  не заменяет источник defaults и не удаляет исходные ключи.
- Повторный запуск открывает существующий record. Неизвестная версия
  или повреждённый record не перезаписываются автоматически.
- Draft и preview используют scoped ключи с `:<id>`. Первоначальные
  unscoped значения читаются только из backup первого владельца.
- Запросы проверяют аккаунт и поколение сессии до применения ответа.
  `_expectedUserId` не позволяет interceptor подставить другой аккаунт
  перед отправкой запроса. Pending timer отменяется при смене аккаунта.

### Сервер

- `GET /user/settings` сохраняет прежний flat-контракт и дополнительно
  возвращает транспортный маркер `_designMigrationVersion: 1`.
  Он не является настройкой дизайна и не включается в outgoing settings.
- Без этого маркера клиент не отправляет миграцию старому backend.
- `POST /user/settings` блокирует строку аккаунта на время транзакции
  (`FOR UPDATE` в PostgreSQL; `IMMEDIATE` в SQLite-проверках).
- Перед первой записью V2 создаётся единственный
  `USER_DESIGN_V1_BACKUP_<id>` с **точной исходной строкой** `setting.value`.
  Уникальный `TMASetting.key` и транзакция защищают создание backup.
- Backup и target либо фиксируются вместе, либо откатываются вместе.
  Невалидный исходный JSON вызывает ошибку, а не запись поверх `{}`.
- Новый V2 получает серверную ревизию. Устаревшая изменённая запись
  получает `409` без частичной записи остальных настроек.
- Повтор того же config/preset после потери ответа не создаёт новой ревизии.
- Успешный ответ содержит `designMigrationVersion: 1` и сохранённый документ.
  Клиент снимает `pending` только после проверки этого подтверждения.
- Старые клиенты могут продолжать писать V1/study-поля: они не удаляют
  и не заменяют V2-документ. Исходный backup при этом не переписывается.

При конфликте новых V2-ревизий локальные изменения накладываются на актуальную
серверную базу по полям. Неизменённые локально поля берутся с сервера.
В конфликте одного поля pending локальное значение остаётся для доставки;
обе исходные версии сохраняются в `backups.conflicts`. Изменение во время POST
остаётся pending после подтверждения предыдущей записи. Ошибки сети/409
не очищают pending; повтор чтения и записи выполняется существующими
действиями sync, visibility/online и ручным сохранением.

До первого подтверждённого серверного переноса повторное чтение учитывает
свежие V1-изменения другого устройства. Pending V2-правки сливаются с ними,
первый серверный snapshot остаётся неизменным, последующие источники сохраняются
в `backups.serverUpdates`. Возврат более старой V2-ревизии также сохраняет текущий
документ в `backups.serverRestores`, а не уничтожает более новый локальный config.

## Восстановление

`GET /user/settings/design-backup` возвращает `{raw: <исходная строка>}`
только для авторизованного аккаунта; при отсутствии backup — `{}`.
ID другого пользователя в query не меняет владельца backup.

Существующий store предоставляет `restorePersonalDesignFromBackup('local')`
и `restorePersonalDesignFromBackup('server')`. Действие преобразует backup
в V2 и сохраняет его локально как pending. Затем обычный
`saveCurrentSettingsToServer()` отправляет новую ревизию. Источники backup
не изменяются; восстановление не возвращает приложение на Legacy runtime.
Это программные действия восстановления, отдельной новой панели UI нет.

Перед ручным восстановлением следует сохранить текущий V2 record, проверить
аккаунт и источник. Публикация/draft сохраняют свой приоритет: восстановленное
личное оформление не публикуется для всех автоматически. Личный сохранённый
preset доступен в существующем меню «Пресет» как «Мой дизайн».
Меню сохраняет прежнюю политику применения секций front/back/cardList;
полный V2 preset, включая упражнения, остаётся в `personalDesignV2.preset`
и может быть целиком применён существующим `setPersonalDesignV2(preset)`.

При восстановлении серверного snapshot до V2 локальный V2 сохраняется,
ожидаемая серверная ревизия начинается заново, прежний документ и прочитанный
snapshot сохраняются в `backups.serverRestores`.
Повреждённые backup/records не следует удалять для обхода ошибки:
их нужно сохранить отдельно и восстановить из подтверждённой копии.

## Что остаётся от Legacy

Сохранены V1 localStorage keys, flat-поля серверного JSON, исходные preset
definitions и временные fallback при недоступной миграции. Converter остаётся
необходимым для однократного переноса и встроенных пресетов. Удалены мёртвые
V1 setters/actions, больше не используемые интерфейсом, и два сброса по версии.
Новые V2-клиенты больше не отправляют flat design / `userDesign` на сервер.

Удаление хранилищ/fallback/adapter — следующий самостоятельный этап только
после подтверждённого rollout, проверки пользовательских копий и восстановления
на разрешённом тестовом PostgreSQL. Legacy-формат карточек к этому не относится.

## Порядок внедрения и следующий этап

1. Сначала выложить backend с атомарной записью, backup и маркером протокола.
2. Затем клиент. До доступности нового backend клиент сохраняет локальные
   исходники и pending V2 и не отправляет миграционную запись старому серверу.
3. Опубликовать единый V2 с явными фонами обеих сторон и выполнить короткую
   проверку запуска, offline/reconnect и смены аккаунта. Ручная проверка переноса
   прежнего личного оформления не является условием внедрения по решению
   пользователя от 2026-10-30. Встроенные backup/CAS/ack не отключаются.
4. Только после подтверждённого переноса и проверки восстановления планировать
   отдельное удаление V1 keys/flat fields/fallback/converter. Этот этап не даёт
   разрешения на удаление production данных.

Commit/push/deploy и миграция реальных пользовательских хранилищ в рамках
работы не выполнялись. Legacy-хранилища и backups не удалены.

и полное равенство остальных config-полей исходному документу.
Главная страница после публикации возвращает HTTP 200.

Откат оформления: прочитать сохранённый backup, проверить текущую ревизию,
затем атомарно заменить config содержимым backup, увеличив revision и обновив
updatedAt. Не возвращать revision назад: клиенты должны увидеть новую публикацию.
Перед откатом сохранить текущий документ; при несовпадении ожидаемой ревизии
остановиться, чтобы не затереть последующие изменения администратора.
Откат deployment выполняется отдельно и не восстанавливает настройки БД.

после этой публикации автоматически не проверялись. Ранее эти сценарии прошли
на синтетических данных. Legacy-хранилища и пользовательские записи не удалены.
