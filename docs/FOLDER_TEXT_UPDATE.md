# Атомарное обновление папки из текстового экспорта

В меню папки доступно **«Обновить папку из файла»**. Один UTF-8 `.txt`/`.md`
проходит существующий parser, общий preview и одно подтверждение. Обновление
затрагивает только явно указанные существующие колоды этой папки и её потомков.

| Режим | Сопоставление | Создание карточек |
| --- | --- | --- |
| Обычный импорт | Все карточки в выбранную колоду, ID игнорируются | Создание, как раньше |
| Обновление колоды | Сохранённый card_id внутри выбранной колоды | Без ID, только явный флажок |
| Обновление папки | Сохранённые deck_id и card_id; backend проверяет дерево | Без card_id, только явный флажок и валидный deck_id |

`# Deck:` служит человеку для навигации. Изменение заголовка не переименовывает
колоду; порядок секций не определяет принадлежность карточек. Повтор одного
deck_id у разных карточек или в разных секциях нормален: это одна группа. Повтор
служебного маркера в одном блоке или card_id в любых колодах файла — ошибка.

## Общая реализация

Сериализатор `cardTextSerializer.js` и извлечение metadata `cardTextMetadata.js`
используются в прежнем виде. `cardTextUpdateParser.js` получил опцию
`requireDeckId`: в folder-режиме каждой карточке нужен ID колоды, включая новые.
Содержимое по-прежнему передаётся существующим batch и exercise parsers.
Локальные ошибки всего файла сохраняют ID колоды и сквозной номер блока.

В `api/services/card_text_update.py` общими для двух режимов стали:

- нормализация, проекция контента, сравнение и счётчики;
- `_preview` для каждой разрешённой колоды;
- `_apply_rows`: UPDATE только разрешённых полей, создание в конец по флажку;
  текущие карточки читаются одним запросом на колоду, затем обновляются по ID;
- `_claim_receipt`: прежняя квитанция `TMAOfflineBatch` и контроль payload hash.

Pydantic-проекции вынесены в `api/routers/card_text_update_models.py`. Роутеры
колоды и папки используют те же строгие ограничения и запрещают технические
поля вроде interval/history/audio. Синхронные handlers владеют connection context.
Миграций PostgreSQL или Dexie нет.

`DeckTextUpdateModal.jsx` и `cardTextUpdate.js` обслуживают оба режима. Folder
режим добавляет общую сводку и сворачиваемые группы колод с карточками «было/стало».
Заголовки групп берутся из доступных записей БД; для недоступной/неизвестной колоды
показывается только присланный ID. Apply — один HTTP-запрос уровня папки:

```text
POST /folders/{id}/text-update/preview
POST /folders/{id}/text-update/apply
```

## Принадлежность и permissions

Backend требует owner/editor на выбранную папку, действующий аккаунт и отдельно
owner/editor на каждую указанную колоду через существующий collaborative guard.
От колоды он идёт по действующим `parent_id` до выбранной папки. Поддерживаются
любые уровни вложенности; удалённый предок, колода снаружи дерева, неизвестный
deck_id, прямой viewer на колоду, чужая приватная колода и подмена deck_id карточки
блокируют всю операцию. Для чужих/недоступных колод не раскрывается учебный текст.
Проверяются все группы, ошибки собираются вместе; разрешённые части не применяются
при ошибке другой группы.

Новая карточка без card_id предлагается отдельно и по умолчанию пропускается.
Если включить добавление, она создаётся в указанной разрешённой колоде. Неизвестный
card_id никогда не превращается автоматически в новую карточку.

## Транзакция, stale protection и повтор

Apply выполняет проверку живых данных, квитанцию, все UPDATE/CREATE нескольких
колод и сохранение результата в **одном `tma_db.atomic()`**. Отдельных транзакций
на колоды нет. На PostgreSQL колоды блокируются по возрастанию ID, затем relevant
предки папок по ID и карточки по стабильному порядку колод/ID. Принадлежность
повторно проверяется из заблокированных значений. Исключение после записей в
последующей колоде откатывает предыдущие UPDATE, CREATE и квитанцию.

Folder fingerprint включает target folder_id, точный входной контент, ID и пути
затронутых колод, их полные снимки учебного контента и состава live-карточек.
Изменение любого затронутого контента/состава, включая пропущенную в файле карточку
затронутой колоды, делает preview устаревшим. Apply возвращает 409 и предлагает
обновить просмотр. Перемещение колоды/предка за пределы выбранной папки также
блокируется. Названия, технические timestamps, SRS, медиа и колоды, отсутствующие
в файле, в fingerprint не входят.

Перед apply общий клиент сохраняет точный request_id и payload в account-scoped
Dexie `folder-text-update:{folderId}`. Серверная квитанция использует namespace
`folder-text-update:{userId}:{requestId}`; deck-mode сохраняет прежний namespace.
Повтор после потерянного ответа/перезагрузки возвращает сохранённый результат:
карточки не создаются повторно, timestamps и позиции не меняются повторно.
Права и membership проверяются также при replay. Прежний request_id с другим
payload запрещён. Квитанция и контент находятся в той же транзакции.

Dirty карточки/колоды и локальные изменения relevant предков требуют синхронизации
перед обслуживанием. Dirty колода вне файла не блокирует операцию. Неразрешённая
сохранённая попытка обновления пересекающихся колод блокирует запуск другого
deck/folder update до проверки её результата. Это сохраняет queued локальную
попытку и предотвращает новый запрос с неизвестным результатом старого.

После успеха кеш контента затронутых колод инвалидируется и списки обновляются.
Сбой обновления списков после commit не вызывает повторного применения.

## Сохранность данных

SRS, intervals, progress всех пользователей, review/edit history, статистика,
learned flags, provenance, медиа, авторство, ownership и позиции существующих
карточек сохраняются. UPDATE ограничен front/back/context, CEFR/topics и связанным
типом/metadata уровня; updated_at меняется у реально изменённых карточек.
Произвольные теги и остальные metadata сохраняются при правке уровня.

Карточка или колода, отсутствующая в файле, остаётся как была. Folder-apply не
изменяет названия, описания, дерево, порядок, папки, колоды или их timestamps.
Legacy deck-apply сохраняет свою прежнюю отметку deck/ancestor updated_at через
`touch_deck_and_parent_folders`. Новые карточки добавляются в конец только явно.

## Размер и границы первой версии

Файл ограничен **5 МБ**, вся папочная операция — **5000 карточек**, действуют
прежние серверные ограничения длины полей. Экспорт папки сам по себе не ограничен
этими пределами и может быть больше. Лимиты не увеличены: большой экспорт нужно
разделить на корректные секции/блоки до лимита. Пропущенные элементы не удаляются,
поэтому последовательное обслуживание частей допустимо.

Работает online в веб-версии. Native/offline update, escaping зарезервированных
строк, merge, backup, rollback UI, версии, удаление, создание/переименование/перемещение
колод и папок не добавлены. Неоднозначные секции остаются ошибкой. Метаданные
контекста интерпретирует существующий parser; перед apply виден полученный контент.
Тесты используют isolated SQLite и browser mock API; конкурентные процессы на
live PostgreSQL не запускались, live данные не изменялись.
