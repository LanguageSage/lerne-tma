# Лог Принятых Решений (Decisions Log)

В данном документе фиксируются основные архитектурные, инженерные и UX решения с датами, контекстом, обоснованием и результатом.

## 📅 Хронология ключевых решений

### 🟢 11 Августа 2026: Защита выбора языка через Telegram CloudStorage + Supabase DB
- **Контекст**: В браузере от Telegram (iOS/Android WebKit) при закрытии Mini App стирался `LocalStorage`, из-за чего приложение каждый раз заново показывало окно выбора языка.
- **Принятое решение**:
  1. Внедрена работа с **Telegram CloudStorage API** (`cloudStorage.set/get`) для дублирования настроек в облако Telegram аккаунта.
  2. Добавлены колонки `active_language` и `has_selected_language` в таблицу `tma_user` в Supabase DB.
  3. Реализована каскадная инициализация: при старте язык восстанавливается из LocalStorage → CloudStorage → Supabase DB.
- **Результат**: Окно выбора языка гарантированно всплывает 1 раз при самом первом входе и больше никогда не беспокоит пользователя.

### 🟢 25 Июля 2026: Миграция с SQLite на PostgreSQL (Supabase Cloud) + Ленивая инициализация
- **Контекст**: Локальный SQLite файл при деплое на Vercel терял таблицы (`no such table: tma_folder`), так как Vercel функции работают в read-only файловой системе.
- **Принятое решение**:
  1. Перевод проекта на PostgreSQL (Supabase).
  2. Внедрение гибридной системы драйверов: `psycopg2-binary` как основной и `pg8000` (чистый Python) как fallback для бессерверной среды.
  3. Перевод `initialize_database()` на ленивый режим без принудительного открытия TCP соединения при импорте модулей, чтобы не возникало таймаутов на "холодном старте" Vercel.
- **Результат**: Стабильная работа API на Vercel с реактивным доступом к областной БД Supabase.

### 🟢 20 Июля 2026: Изоляция контента по языкам обучения (`target_language`)
- **Контекст**: Колодки и папки немецкого, английского и норвежского языков перемешивались на одном экране.
- **Принятое решение**:
  1. Добавление колонки `target_language` для `tma_deck`, `tma_folder`, `tma_custom_prompt`.
  2. Фильтрация данных на уровне SQL-запросов и сервисов.
  3. Автоматический перезапрос данных колод при смене активного языка в UI.
- **Результат**: Каждое языковое пространство (DE 🇩🇪, EN 🇬🇧, NO 🇳🇴) стало изолированным и чисто структурированным.

### 🟢 15 Июля 2026: Оптимизация Инициализации через Эндпоинт `/api/init`
- **Контекст**: При запуске приложения фронтенд делал 4 отдельных HTTP запроса (за колодами, папками, настройками и промптами), создавая задержки на мобильных сетях.
- **Принятое решение**: Создание единого консолидированного эндпоинта `/api/init`, отдающего колоды, папки, настройки и промпты в 1 пакетном запросе.
- **Результат**: Ускорение загрузки приложения на 70%.

### 🟢 10 Июня 2026: Автономная система интервальных повторений SM-2 и Индексация
- **Контекст**: Требовалось реализовать эффективный подсчет карточек на повторение без нагрузки на сервер.
- **Принятое решение**:
  1. Реализована классическая схема SuperMemo-2 (`ease_factor`, `interval`, `repetitions`).
  2. Добавлены составные индексы в PostgreSQL (`idx_tma_card_deck_deleted`, `idx_tmaprogress_queue_review`).
- **Результат**: Выборка карточек на повторение происходит за <5 мс даже при десятках тысяч карточек.

### 🟢 13 Сентября 2026: Святость пользовательских данных и запрет деструктивных скриптов
- **Контекст**: Скрипты массовой синхронизации (вроде `restore_all_users_lid.py`) удаляли и перезаписывали содержимое колод пользователей из устаревших шаблонов, стирая ручную сортировку и правки карточек.

  2. Ручные правки и сортировка пользователя в БД имеют абсолютный приоритет.
  3. Все устаревшие и опасные скрипты синхронизации из `tools/` удалены из проекта.
- **Результат**: Данные пользователей гарантированно защищены от случайной перезаписи или потери.

### 🟢 13 Сентября 2026: Единый источник правды (Single Source of Truth) для карточек
- **Контекст**: Ранее в проекте сосуществовали внешние JSON-справочники (`lidQuestions.json`) и база данных. Попытки подгружать данные вопросов из JSON приводили к рассинхронизации и потере картинок.
- **Принятое решение**:
  1. Единственным источником правды для карточек, вариантов ответов, переводов и медиа является база данных: `tma_card` (на сервере) и Dexie `cards` (на клиенте).
  2. Внешний файл `lidQuestions.json` и все завязанные на него вспомогательные скрипты полностью удалены из репозитория.
  3. Симуляторы экзаменов и тренировки получают данные исключительно через сериализацию реальных объектов карточек из БД.
- **Результат**: Полная согласованность данных, отсутствие дублирующих файлов, архитектурная чистота.

### 🟢 13 Сентября 2026: Унификация медиа-архитектуры через серверную таблицу `tma_media`
- **Контекст**: Изображения частично лежали в статической папке фронтенда `app/public/lid_images/`, а частично отдавались через эндпоинт `/api/media/images/`. Это приводило к сбоям загрузки при генерации динамических уроков.
- **Принятое решение**:
  1. Все 42 оригинальных изображения загружены в БД в таблицу `tma_media`.
  2. Папка `app/public/lid_images/` полностью удалена из проекта.
  3. В карточках сохраняются только чистые имена файлов (например, `q148.197dc41c.png`), а фронтенд и API канонически строят URL через `/api/media/images/<filename>`.
  4. Костыли с fallback-обработчиками ошибок картинок в UI удалены.
- **Результат**: Унифицированная архитектура медиа, готовая к динамическим пользовательским урокам любого масштаба.

### 🟢 13 Сентября 2026: Сохранение скролла и выбранной карточки в `CardList`
- **Контекст**: При возврате из режима обучения (`StudyView`) или редактора карточки список карточек сбрасывался в самое начало, заставляя пользователя снова скроллить сотни элементов.
- **Принятое решение**:
  1. В `CardList.jsx` стейт скролла `cardsScrollTop` и идентификатор активной карточки `lastSelectedCardId` сохраняются в хранилище.
  2. При монтировании списка виртуализированный/пагинированный рендер гарантирует отрисовку элементов вплоть до позиции активной карточки (`idx + 30`).
  3. Слушатель скролла защищён флагом `isRestoringScrollRef` от преждевременного сброса координаты в 0 при повторном открытии.
- **Результат**: Бесшовный возврат в точное место списка карточек без рывков и потери контекста.

### 🟢Отменено безусловное удаление аудио.
Старый и новый текст лицевой стороны сравниваются после нормализации произношения (_prepare_tts_text).
Если в карточку добавили фигурные скобки {} для тренажёра, добавили вопрос в скобках с новой строки \n(...) или изменили только контекст/перевод — произносимый текст не изменился, и существующая озвучка бережно сохраняется.
Озвучка инвалидируется только тогда, когда пользователь действительно изменил сами произносимые слова (например, Ich gehe →→ Wir fahren).


### 🟢 Применяются ли настройки ИИ ко всем пользователям?
Да, абсолютно верно.
Изменять глобальный провайдер ИИ (AI_PROVIDER), ключи API и вызывать выбор модели (DEFAULT_MODEL) можете только вы — в бэкенде установлена строгая проверка доступа по вашему ADMIN_USER_ID (if user_id != ADMIN_USER_ID: raise HTTPException(403)).
Когда вы в админке меняете провайдера (например, с Google на Groq) или выбираете другую модель, эти параметры сохраняются как глобальные.
Все обычные пользователи приложения при создании/генерации карточек автоматически используют выбранную вами единую модель и настройки.

### 🟢Где хранятся настройки:
Настройки провайдеров и выбранная модель ИИ (AI_PROVIDER, DEFAULT_MODEL, ключи API) записываются в БД PostgreSQL (в таблицу tma_setting).
Персональные пользовательские настройки (авто-режим, цвета, карточки) хранятся в БД под вашим ID (USER_SETTINGS_<user_id>), а также дублируются в IndexedDB (Dexie) в вашем браузере.

### 🟢Сохранятся ли настройки они при откате версии сервера:
Да, гарантированно сохранятся.
Откат кода на сервере (через git checkout или пересборку бандла) заменяет только программные файлы (.py, .jsx), но не трогает данные внутри базы PostgreSQL.
Записи в таблице tma_setting останутся на месте, и при откате кода сервер прочтёт ровно ту модель и те ключи, которые вы сохранили в БД.
