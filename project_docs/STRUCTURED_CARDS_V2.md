# Структурированные карточки V2 — переход к единому нативному формату

> **Новое решение от 2026-11-05 — работа в ветке `feature/native-structured-cards-v2`.**
> Целевая архитектура: два входа (`Lerne Codex` текстовый FRONT/BACK/CONTEXT и JSON V2) → один валидированный нативный V2 → сохранение, API, Dexie, рендеринг, редактор, экспорт и резервное копирование в едином V2-контракте. Обратная компиляция V2 в legacy DSL исключается из рабочего конвейера. Тип карточки задаётся явным `type`, а не определяется из текста.
> Старые карточки в локальных данных должны быть мигрированы в V2 с сохранением ID, прогресса, заметок, медиасвязей и порядка. Неоднозначные преобразования нельзя выполнять с потерей данных: сохранять исходник для восстановления, выдавать диагностические ошибки и требовать исправления. Не включать смешанный runtime V1/V2.
> Переход внедряется целиком в отдельной ветке и тестируется локально; `main` и production не меняются до полной приёмки. Это **целевое решение, не утверждение о завершённой реализации**.
>
> **История:** 2026-10-16 нативное хранение было заморожено и принят Option B (V2 authoring → legacy DSL). Решение от 2026-11-05 отменяет эту архитектурную цель **для новой ветки**; описание ниже фиксирует предыдущее состояние и требует актуализации по мере реализации.

> **Предыдущее состояние конвейера (решение от 2026-10-16).**
> Прежний прототип (`content_v2`, миграция 87, `legacy_card_writes`, `/sync/v3`, CAS-ревизии и native writes) был остановлен. Его миграция 87 исключена из текущего плана.
> Рабочая публикация пока следует **Option B (Authoring V2 JSON → детерминированная компиляция в существующий DSL)**:
> ИИ или автор создаёт карточки в строгом контракте V2 JSON → `structured_cards_v2.py` валидирует структуру → `structured_cards_legacy.py` (`to_legacy_card` / `to_legacy_document`) компилирует карточку в существующий DSL (`FRONT`/`BACK`/`CONTEXT`/`metadata`) с обязательной round-trip проверкой (`parse_exercise_content`, `detect_card_type`, `detect_ai_input_type`) → сохранение идёт через стандартный конвейер публикации (`author_service.py` → `bulk_save_cards`) без изменения схемы БД, синхронизации, офлайн-режима или SRS.

V2 — JSON-контракт для авторства уроков человеком и ИИ. Тип задан явно; ответы и данные упражнения не извлекаются из текста `FRONT`. В «Авторе уроков» доступны как предварительный просмотр JSON V2 (`/api/admin/author/v2-preview`), так и разбор/публикация V2 JSON через `author_service.parse_document`.

## Этап 1. Единый импорт в V2

`api/card_core/lerne_card_core/structured_cards_import.py` предоставляет
`import_documents(text, *, default_deck_name=None, json_input=False)`.
Результат — упорядоченный список валидированных `Document` с `schema_version: 2`.
JSON V2 описывает одну колоду. Codex может содержать несколько колод в исходном
порядке. Для Codex без заголовка CLI берёт название из имени файла или
`--deck-name`. Текст распознаётся по формату, а расширение `.json` в CLI
требует строгого JSON. Ошибка в любой колоде прерывает весь импорт.

- JSON проходит валидацию V2 напрямую. Строки и явный тип сохраняются, включая
  буквальные маркеры и Quiz с несколькими правильными вариантами.
- В Codex FRONT разбирается на информационные блоки и одно упражнение на входной
  границе. CONTEXT переносится в `explanation`, а уровень и тема извлекаются
  отдельно. Явная тема Codex остаётся одним значением, включая запятые.
- Оба входа разрешают наследование из паспорта одинаково. Явные уровень и темы
  сохраняются, в том числе пустой массив тем. Ссылки на изображения остаются
  в `card.image`. Codex `::card_id` становится строковой ссылкой `card.id`,
  а `::deck_id` и заголовок папки сохраняются в `deck.metadata.source_deck_id`
  и `deck.metadata.source_folder_name`. Эти поля описывают источник импорта.
- Trainer, Quiz и Match сохраняют текст BACK в `data.back_note` отдельно от
  ключей ответов. Quiz может иметь пустой `data.prompt`, если вопрос вынесен
  в `info.task` или `info.source`. Codex Quiz требует ровно один правильный
  вариант согласно текстовому контракту. В Word Bank одинаковые копии
  расходуются слева направо по порядку пропусков, а конфликтующие варианты
  с одинаковым нормализованным ключом вызывают ошибку.
- Конфликтующие маркеры, неполные ключи, дубли полей и некорректные паспорта
  останавливают импорт с указанием колоды и поля или карточки. Документ
  Codex только с паспортом требует отдельной операции обновления паспорта.
- Точка входа этапа 1 — чистый импортёр и команда ниже. Действующие операции
  публикации пока используют прежний контракт записи. Подключение нативной
  записи к рабочим точкам входа зависит от следующих этапов.

```powershell
python scripts/structured_cards_v2.py import lesson.txt --deck-name "Урок 1"
python scripts/structured_cards_v2.py import lesson.json
python -m unittest scripts.tests.test_structured_cards_import scripts.tests.test_structured_cards_v2 -v
```

## Этап 2. PostgreSQL и граница хранения

**Источник содержимого** — `tma_card.content_v2 JSONB`. Значение имеет форму
`{"schema_version": 2, "card": <Card>}`, где `Card` — проверенный контракт
этапа 1. Версия лежит в самом конверте. У каждой нативной карточки SQL
`NULL` в `front_text`, `back_text`, `context`, `card_type`, `topics`, `tags`
и legacy `metadata`. В строках, ожидающих миграции, `content_v2` равен SQL
`NULL`, а legacy FRONT/BACK и тип обязательны. PostgreSQL CHECK проверяет
взаимоисключение форматов и основные поля конверта, в том числе отсутствие
дополнительных полей на его верхнем уровне. Pydantic проверяет весь Card при
чтении и записи, включая тип, ответы, информационные блоки и метаданные.

`tma_card.id` остаётся числовым первичным ключом. Колода, позиция, автор,
источник создания, история, отметка удаления, физические медиа и связи по
`card_id` остаются в существующих полях и таблицах. `Card.id` и `Card.image`
внутри JSON — авторская ссылка и ссылка на источник изображения при импорте.
Привязанное к записи медиа по-прежнему находится в `image_path`,
`image_data` и путях аудио/видео. Этап 7 должен отдельно сопоставить
legacy-политику проверки, CEFR, метки и остальные метаданные с V2, с
диагностикой при конфликте.

**Почему изменён прежний план.** Прототипы `5c077d3` и `a92efc9` выявили
старые полнострочные записи и списки полей в Admin, копировании, sync и
восстановлении. Они могли потерять V2 или оставить устаревшую проекцию.
Поздний результат TTS мог привязать аудио предыдущей редакции. Новый план
оставляет один редактируемый JSONB, без сохраняемой текстовой проекции,
флага legacy-записи или общей ревизии строки. До переключения рабочие
пути продолжают работать с legacy-данными. Перед конвертацией этап 7 должен
остановить старые writers и согласовать незавершённые клиентские записи,
а также проверить копирование, восстановление и привязку медиа. После
конвертации конечная схема оставляет `content_v2 NOT NULL` и убирает
legacy-колонки содержимого. Условия конкурентного обновления для API и
протокола sync относятся к соответствующим этапам.

**Операции хранения** в `api/services/structured_card_storage.py` создают,
читают и целиком заменяют V2. Они различают отсутствие активной нативной
карточки и ошибки валидации. Запись присоединяется к внешней транзакции
вызывающего кода через savepoint. Замена обновляет только JSONB и
`updated_at` одним условным UPDATE. Внешний слой отвечает за авторизацию,
позицию, политику конфликтов, связанные записи и обновление медиа.

**Миграция 93** добавляет колонку без значения по умолчанию и CHECK в одной
транзакции с записью в `tma_migration_history`. Advisory lock сериализует
запуски, таймауты ограничивают ожидание и выполнение DDL, а повторный запуск
проверяет колонку и наличие валидированного ограничения. Поддержаны прежняя
схема и пустая схема из текущих ORM-моделей. Существующие строки не
конвертируются. Миграция включена только в PostgreSQL LOCAL bootstrap и
доступна через явный вызов `run_structured_cards_v2_migration`. Она не входит
в обычный каталог миграций startup. Для приёмки используется отдельный
кластер на loopback с синтетическими карточками. Контракт схемы TMA
для Admin обновлён до версии 4. Согласование потребителя запланировано
на этап 5.

```powershell
python scripts/tests/structured_cards_postgres.py --bin-dir <путь-к-postgresql-bin>
```

**Расширение для речи.** Инструкции к выборочной озвучке, устным заданиям и
диалогам смогут стать типизированными полями контракта Card в том же JSONB.
Селекторы будут ссылаться на существующие поля или стабильные ID частей,
когда появятся повторяемые сегменты. Порядок реплик и учебные условия
принадлежат Card, а созданные аудиообъекты, попытки и прогресс связываются с
`card_id` снаружи. Для этих расширений не нужны новые колонки содержимого
или дублирование текста. На этапе 2 контракт авторства речи не вводится.

## Этап 3. HTTP API карточек

Существующие URL TMA принимают конверт `content_v2: {"schema_version": 2,
"card": <Card>}`. Запросы проверяют `Card` из `lerne-card-core` и отклоняют
лишние поля. Ответы карточек включают ID записи, колоду, позицию, `content_v2`,
непрозрачную `revision` и применимые поля медиа и прогресса. Учебные поля
возвращаются в `Card`; буквальные DSL-маркеры остаются текстом.

| Маршрут под `/api` | Контракт |
| --- | --- |
| `POST /cards/save` | Создание. `request_id` (UUID), `content_v2`, необязательные `deck_id`, `after_card_id` и пути медиа. Без колоды используется Inbox. |
| `GET /cards/{id}`, `PUT/PATCH /cards/{id}` | Чтение и полная замена содержимого. Для замены нужны `request_id` и текущая `revision`. Колоду меняет перенос. Отсутствующие пути медиа сохраняются, явный null удаляет ссылку. |
| `POST /cards/bulk-save` | `import_id` (UUID), `cards` с `deck_id` для новых или `card_id` и `revision` для существующих. `placement: start` применяется к новым карточкам одной колоды. Весь пакет фиксируется одной транзакцией. |
| `POST /cards/batch-copy`, `batch-move`, `reorder` | `request_id`, упорядоченные `card_ids`, для копирования/переноса — `target_deck_id` и `on_duplicate`. Копирование создаёт ID, перенос сохраняет ID и связанные записи. Дубликат определяется по полному V2. При совпадении `overwrite` для переноса отклоняется, чтобы не потерять ID и прогресс; при копировании он может только заполнить отсутствующие медиа. |
| `DELETE /cards/{id}`, `POST /cards/batch-delete` | Мягкое удаление. Одиночный запрос передаёт ревизию в кавычках в `If-Match`; пакет передаёт `request_id`, `card_ids` и `revisions` по ID. |
| `GET /decks/{id}/cards`, `/decks/{id}/next`, `/study/card/{id}`, `/cards/search`, `/cards/duplicates`, `/study/duplicates/next` | Чтение и подбор V2. Списки исключают legacy-строки. Прямое чтение legacy после проверки доступа возвращает `409 card_requires_migration`. |
| `POST /decks/import-json`, `POST /decks/{id}/copy` | Импорт с `import_id` и `document` (V2 Document) или `codex` (текст, опционально `default_deck_name`); копирование с `request_id` и необязательным `folder_id`. Колода, содержимое и квитанция фиксируются вместе. |
| `POST /ai/evaluate-answer` | Free Text и Editable Text берут задание, образец/исправление, варианты и политику из `Card`. Расчёт оценки и запись SRS используют действующий механизм. |

Запись через `structured_card_api.py` переиспользует хранилище этапа 2,
права колод и квитанции `TMAOfflineBatch`. Колоды и карточки блокируются
в порядке ID, право доступа проверяется перед записью и воспроизведением
квитанции. Изменённые данные с тем же ключом и устаревшая ревизия дают
`409`. При ошибке пакета откатываются карточки, квитанция и метки времени
колод. Чтение и копирование доступны viewer, редактирование исходника
и перенос требуют owner/editor. Флаги и оценки остаются персональными.

К завершению этапа 3 браузерный клиент ещё ожидал legacy-поля. Sync со старым
контрактом возвращает `409 native_card_requires_v2_sync`
при попытке передать нативную карточку. Legacy text-update, импорт общих
материалов и каталог защищены от изменения нативного содержимого, пока их
контракты не будут перенесены. Этап 7 переносит
сохранённые V1-карточки. Тесты SQLite старого сквозного HTTP-контракта
`test_critical_http` и `test_db_workers` ещё используют legacy-поля записи
и автоматический TTS при сохранении. Новый контракт проверяется по сокету
с настоящими bearer-сессиями и одноразовой PostgreSQL.

```powershell
python scripts/tests/structured_cards_postgres.py --bin-dir <путь-к-postgresql-bin> --http
```

## Этап 4. Отображение в React

Учебные экраны принимают `content_v2.card` из API. `structuredStudyCard.js`
извлекает текст физической стороны, информационные блоки и параметры
упражнений. Theory и Standard отображаются непосредственно в `StudyCard`.
`ExerciseRenderer` передаёт остальным семи типам авторские части, ответы,
варианты, пары и токены. Режимы изучения сохраняют авторский тип карточки.
Состояние попытки хранит ввод и результат
проверки в рамках review. Design V2 по-прежнему определяет оформление.
Старые предпросмотры редактора и дизайна используют прежний разбор
авторского текста.

Учебная навигация и оценка SRS используют существующие маршруты. При
`409 card_requires_migration` или `deck_requires_migration` интерфейс
сообщает о переносе и предлагает вернуться к колодам. Смешанная колода
доступна для изучения в пределах карточек V2. Редакторы и офлайн-контракт
переносятся на следующих этапах.

Привязанное аудио воспроизводится для физической стороны. Существующий
`/media/generate-card-audio` берёт текст из V2 и привязывает результат,
если содержимое и путь аудио совпадают со снимком до генерации. Привязка
медиа и сохранение пояснения из учебного экрана используют ревизию из API.

Браузерный сценарий `native-structured-study.spec.cjs` проверяет все девять
типов, проверку ответов, оценки и переходы, аудио и изображение, сообщение
о переносе и адаптивность. HTTP-тест на PostgreSQL проверяет получение
V2, ошибку для колоды V1 и привязку аудио с подменой TTS-провайдера.

Старые браузерные сценарии Word Bank в `exercise-feedback.spec.cjs`
и Match в `match-quiz-feedback.spec.cjs` требуют нативных фикстур.
В профильном прогоне Word Bank остановился на сообщении об отсутствии
V2. Сценарий Match остановился при входе, до открытия legacy-карточки.

## Этап 5. Редакторы и публикация

TMA держит один черновик `content_v2`. Типизированные поля меняют только
выбранные части `Card`; метаданные и поля медиа сохраняются при правке.
Создание передаёт `request_id`, правка также передаёт ревизию. При конфликте
черновик остаётся открытым, а повторное открытие карточки получает актуальную
версию. Предпросмотр и сохранение проверяют карточку серверным контрактом.
Стандартную карточку можно заполнить вручную, диктовкой или через генерацию
по введённой фразе. Результат генерации проходит проверку до попадания в
черновик или в пакетную запись.

Предпросмотр импорта использует общий парсер Lerne Codex и JSON V2.
Быстрый импорт отправляет валидированные карточки в существующий пакетный
маршрут, публикация урока использует канонические документы. Нативные
операции записи идут по сети, синхронизация относится к этапу 6.

Независимый Admin устанавливает проверенный wheel `lerne-card-core==0.1.4`.
В колодах TMA Admin использует `content_v2` и ревизию, с отдельной проверкой
каталога миграции 93 перед записью. Стандартная карточка имеет поля быстрого
редактирования, полный JSON доступен для всех девяти типов. Старая
библиотечная таблица не входит в схему 93. Устаревшие операции пакетной
перегенерации, обновления и переноса материалов требуют отдельного переноса
на нативный контракт. Обновлённые браузерные сценарии Word Bank и Match
проходят с нативными данными и авторизацией тестового аккаунта.
Историческая проверка `verify_admin_contract.py` фиксирует изменение
fingerprint импорта. Совместимость отдельной операции `native_cards`
проверена независимо на одноразовом PostgreSQL.

## Этап 5B. Пакетные операции и библиотека Admin

Таблицы учебных и библиотечных карточек хранят одинаковый JSONB-конверт
`{"schema_version":2,"card":{...}}`. Миграция 94 добавляет `card.content_v2`
и ограничение единственного источника содержимого для библиотечной таблицы.
Её локальный запуск сохраняет существующие строки, ключи, колоды и медиа.
В Admin идентификатор библиотечной колоды имеет префикс `lib_`, чтобы разделять
числовые пространства таблиц. Библиотека и учебные колоды используют одну
транзакцию PostgreSQL при переносе. Точное совпадение канонических карточек
сохраняет ID учебной копии и связанный прогресс. Явная замена скрывает лишние
строки мягким удалением. Редактирование карточек V1 ожидает миграции данных.

Пакетное обновление Admin использует предпросмотр с ревизиями и запись
результата запроса в той же транзакции. Для изменения существующей карточки
нужен её ID либо однозначное точное совпадение при импорте папки.
Перегенерация меняет только разрешённые поля: пояснение, уровень и, для
подходящих типов, перевод или примечание. Данные упражнения, расширения и
остальные медиа сохраняются. Ревизия защищает от параллельного редактирования.
Для утверждённой пробной генерации повтор запроса использует запись результата
в PostgreSQL. CEFR-классификация обновляет `card.level` и `card.metadata.cefr`.

## Этап 6B.1. Офлайн-создание одной Standard-карточки

- Обычный редактор передаёт нативный конверт `content_v2` и UUID запроса
  в `POST /cards/save`. При отсутствии сети или неопределённом результате
  сетевой записи Standard можно сохранить в доступную на устройстве
  серверную колоду. Офлайн доступны поля Standard и ссылки на привязанные
  медиа. Новая колода и вставка после ещё не подтверждённой карточки
  требуют предварительной синхронизации.
- `offlineApi` записывает карточку с отрицательным ID и неизменяемый payload
  в существующие `cards` и `syncState` одной транзакцией Dexie аккаунта.
  UUID и исходный payload сохраняются при перезапуске и повторе. Операция
  обозначена ключом `card-create-v2:<request_id>`. Ошибка сохраняет карточку
  и операцию. Интерфейс различает ожидание, ошибку и подтверждение.
- `syncService` доставляет операцию тем же авторизованным `/cards/save`.
  Нативный API повторно проверяет доступ и содержимое. Квитанция
  `cards-v2:save:<user_id>:<request_id>` в `TMAOfflineBatch` фиксируется вместе
  с карточкой PostgreSQL. Тот же запрос возвращает тот же серверный ID.
  Клиент завершает операцию только после одной транзакции, которая заменяет
  временную строку серверной, сохраняет `aliases.cards` и снимает ожидание.
  Успех этой транзакции не зависит от результата последующего pull.
- `GET /sync/v2/pull?card_schema=2` передаёт нативные карточки и связанные
  записи прогресса с обычной серверной проверкой доступа. Старые клиенты
  продолжают получать прежний ответ. Существующие локальные V1-карточки,
  их прогресс и операции сохраняются. Сохранённый legacy-пакет с такими
  операциями остаётся в исходном виде и не блокирует доставку V2-создания.
- Офлайн-редактирование, конфликты версий и перенос очередей V1 относятся
  к следующим этапам. Цветная метка и автоматическая генерация аудио
  остаются функциями создания по сети.

## Исходная архитектура до перехода

| Путь | Владелец и ограничения |
| --- | --- |

| «Автор» / CLI | `api/services/author_service.py`: документ с колодами и паспортами (в формате Lerne Codex или V2 JSON), наследование уровня/темы, сохранение через `bulk_save_cards`. |

## Документ

```json
{
  "schema_version": 2,
  "deck": {"name": "Немецкий: прошлое"},
  "cards": [{
    "id": "past-mixed-1",
    "type": "trainer",
    "info": [{"type": "task", "text": "Ergänzen Sie den Satz."}],
    "data": {
      "parts": [
        {"type": "choice", "options": [
          {"text": "Als", "correct": true}, {"text": "Wenn"}
        ]},
        {"type": "text", "text": " ich ankam, "},
        {"type": "input", "answers": ["hatte"]},
        {"type": "text", "text": " sie schon gegessen."}
      ]
    },
    "explanation": "Als — однократное событие в прошлом."
  }]
}
```

Один документ описывает одну колоду и непустой список карточек в учебном порядке.
Обязательны `schema_version`, `deck.name`, `cards`, `card.type`, `card.data`.
`schema_version` — целое `2`; неизвестные поля и типы запрещены, значения не приводятся автоматически из строк/чисел/bool. Пустой обязательный текст запрещён.
Строки содержат обычный текст/Markdown; маркеры legacy не имеют специального значения в V2. Никакого шаблона `{{gap}}` и повторного разбора строки не требуется.

Общие необязательные поля карточки:

| Поле | Значение |
| --- | --- |
| `id` | Непустая строка, уникальная внутри документа; авторская ссылка, не ID записи БД. |
| `info` | Упорядоченные информационные блоки перед упражнением: `{type: task/source/example, text}` либо `{type: options, items: [...]}`. Блоки можно повторять. Их текст не определяет тип карточки. |
| `explanation` | Пояснение после ответа, соответствует legacy CONTEXT, по умолчанию `""`. |
| `level` | CEFR A1–C2; отсутствие или null наследует `passport.intro.level`. |
| `topics` | Массив непустых строк; отсутствие или null наследует `[passport.intro.topic]`, `[]` явно снимает темы. |
| `metadata` | JSON-объект расширений: происхождение, теги, авторские заметки. Не место для второго экземпляра содержимого/ответов. |

## Данные всех типов

| `type` | Обязательные данные в `data` | Ответ / дополнительные данные |
| --- | --- | --- |
| `theory` | `text` | Необязательный `summary` — оборот карточки, по умолчанию пустой. Примеры с пропусками в тексте остаются теорией. |
| `standard` | `prompt`, `answer` | Текст вопроса и оборот. |
| `trainer` | `parts` | Последовательность text/input/choice, минимум один пропуск. Режим определяется каждым пропуском, смешанный Trainer не требует отдельного типа. Необязательный `back_note` сохраняет оборот. |
| `quiz` | `prompt`, `options` | Минимум два `{text, correct?}`. `correct` по умолчанию false, минимум один true; в legacy-проекции требуется ровно один правильный вариант. Вопрос можно вынести в `info.task` или `info.source`. Необязательный `back_note` сохраняет оборот. |
| `match` | `pairs: [{left, right}, ...]` | Минимум две пары. Пары и их порядок сохраняются, включая повторы. Необязательный `back_note` сохраняет оборот. |
| `puzzle` | `tokens: ["Ich", "bin", "angekommen."]` | Непустой массив токенов в правильном порядке. Необязательный `translation`. |
| `word_bank` | `options: ["habe", "bin", ...]`, `parts` | text либо `{type: "gap", option: 0}`. `option` — индекс правильного элемента options с нуля, один элемент расходуется один раз. |
| `free_text` | `prompt`, `sample_answer` | Образец не является точным ключом. Необязательные `accepted_answers`, `grading_policy` используют действующий контракт. При отсутствии политики используется `mode: open_text`. |
| `editable_text` | `source_text`, `correct_text` | Ошибочный текст предзаполняет поле; BACK хранит полное исправление. Необязательные `accepted_answers` и `grading_policy`; по умолчанию `controlled_text`, без зачёта опечаток. Перевод до проверки — `info.source`. |

## Реализация и запуск

Match компилируется в строки `left => right`. Первый `=>` задаёт границу пары;
все последующие `=>`, `->`, `—` и `=` справа сохраняются как текст. Символы
`->`, `—` и `=` допустимы и слева, но буквальный `=>` слева неоднозначен и вызывает
ошибку преобразования с путём поля. Переносы строк, краевые пробелы и разметка,
которую legacy-парсер удаляет, по-прежнему отклоняются. Единственный разделитель
пары — `=>`; строки с `->`, `—` или `=` без `=>` не считаются парами.

- `api/services/structured_cards_v2.py`: строгие Pydantic-модели всех 9 типов, `validate_document(dict)`, `load_document(json_text)`, `validate_card(dict)`, `load_card(json_text)`, `normalize_card(card)` и генерируемая JSON Schema.
- `api/services/structured_cards_legacy.py`: `to_legacy_card(card, deck, index)` и `to_legacy_document(dict | Document)` для всех девяти типов с проверкой `parse_exercise_content`, `detect_card_type` и `detect_ai_input_type`.
- `api/services/author_service.py`: `parse_document` прозрачно принимает как текстовый формат Lerne Codex, так и V2 JSON (компилируя его через `to_legacy_document` и сохраняя `metadata` при публикации).
- `tools/admin/services/structured_preview.py` и `POST /api/admin/author/v2-preview`: покарточный предпросмотр V2 JSON без записи в БД.
- `scripts/structured_cards_v2.py`: CLI (`import`, `validate`, `to-legacy`, `schema`).

```powershell
python scripts/structured_cards_v2.py validate local/test-data/examples/structured_cards_v2/basics.json
python scripts/structured_cards_v2.py to-legacy local/test-data/examples/structured_cards_v2/basics.json
python scripts/structured_cards_v2.py schema
python -m unittest scripts.tests.test_structured_cards_v2 scripts.tests.test_structured_preview -v
```
